# Defect causes: from a symptom to a candidate cause, and the check that settles it

*Part of the iXBRL Skill by Max Schoon, Founder, Doc2iXBRL — <https://doc2ixbrl.com>. Licensed CC BY 4.0. If you use this material, you must credit it (see `ATTRIBUTION.md`).*

**Load this when** you hold a symptom and want candidates: a validator code from a run you can reproduce, or a defect visible in the rendered statements that no validator reported, or a package that a receiver refused on shape. The rows map each symptom to the conversion-pipeline stages that plausibly produced it, and give the check that confirms or refutes each candidate.

**Do not load this when** the question is what a rule says (that is `references/validation.md` for codes, `references/esef.md`, `references/dimensions.md`, `references/spec.md` and the jurisdiction files for the rules behind them), how to author something correctly (`references/conversion.md`), or which taxonomy version was operative (`references/dts.md`). This file is a lookup for diagnosis, and it deliberately holds no rule text of its own.

## How to read a row

A matching row yields **candidate causes, never a verdict**. Confirm one with its check before changing anything: a cause without a passing check is a guess with a citation attached. If the check refutes the candidate, take the next one; if every candidate is refuted, the symptom needs a new row, not a forced fit into the nearest one.

For a symptom with no row here, work from `references/validation.md` and the specification, not from the row that looks closest. A row may say the cause is not known: that is an honest answer, and forcing a fit is worse than recording the symptom.

Keep evidence and authority apart. A code proves that a validator implementation flagged something. The specification, the reporting manual and the filing rules are the rule. Before calling a finding a defect, quote the log line verbatim and look the code up in the operative instrument; rule numbers are renumbered between releases, and several codes in circulation are implementation-only (`references/jurisdictions/dk-erst.md` § The ERST Kontroller corpus: the filing-rules authority, and § Validation in `references/jurisdictions/uk-frc.md`, both say so about their own regimes).

Every check below assumes a reproducible run: the same processor release, the same plugin and profile selection, the same taxonomy packages, resolved the same way. A validation result is only meaningful with the inputs that produced it, and `by_source` in a DTS profile tells you whether bytes came from a package, a cache or the network (`references/dts.md` § Working with `scripts/dts_profile.py`).

## Pipeline stages

The cause column names a stage, never a product, a module or a file in anyone's codebase. These thirteen stages are the whole vocabulary it uses; they are the points at which a conversion can decide something, so they are the points at which a fix can land.

1. **Source intake and text extraction**: bytes in, characters and positions out.
2. **Statement and table recognition**: which region is a primary statement, which cells are its rows and columns.
3. **Concept selection (mapping)**: which QName a recognised row binds to.
4. **Period and context assignment**: instant or duration, which dates, which entity identifier, which dimensional members.
5. **Unit, scale and decimals**: which measure, which power of ten, which declared accuracy.
6. **Sign and label role**: the canonical value's sign, and the preferred label that renders it.
7. **Calculation-network generation**: summation-item arcs, weights, and which arcrole they use.
8. **Presentation-network generation**: the tree, its roots, its preferred labels.
9. **Dimensional (definition) network and anchoring**: hypercubes, domains, defaults, and the anchoring arcs a regime requires.
10. **Hidden section and transformations**: what goes in `ix:hidden`, and which transformation renders a value.
11. **Extension taxonomy authoring**: the filer's schema, its labels, its roles.
12. **Package assembly and DTS resolution**: the archive, its manifests, its catalog, and what the pointers resolve to.
13. **Validation invocation**: the profile, the plugins, the taxonomy packages and the calculation mode handed to the validator. A wrong verdict from here is not a defect in the report.
